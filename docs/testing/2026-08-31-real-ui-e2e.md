**Verdict: FAIL. The product did not complete its core goal-to-working-change workflow.**

## Reproduced defects

### E2E-01 — P1: ordinary goals fail before execution

**Reproduce:** New run → connect calculator repository → enter normal goal above → Start run → Planning → Failed.

No tasks, implementation, tests or deliverable artifacts were produced. The diagnostic retry failed in the same part of the workflow. Dispatcher logs show that the generated task plan violated the execution-policy validator:

```text
Normal run:
MISSING_STAGE_TOOL:DOCUMENTATION stages require tools ['run_tests']
MISSING_STAGE_TOOL:VALIDATION stages require tools ['read_file']

Diagnostic retry:
MISSING_STAGE_TOOL:RESEARCH stages require tools ['search_code']
```

Both architect stages are recorded as failed. Plan generation and repair need to satisfy the existing execution policy; the evidence does not justify weakening the validator. Source: `planning/validator.py:244`. **Impact:** the central workflow cannot reach coding, testing or completion in these two real attempts.

### E2E-02 — P1: saved model settings do not control actual planning

**Reproduce:** Model settings → select Gemma → Test connection succeeds → Save & Apply Model → launch work.

The sidebar and launch form show Gemma, but all six calls across the two implementation attempts used Nemotron. Reopening settings and signing in from a fresh tab still showed saved Gemma before restoration.

`apps/api/routes.py:163` updates the API process's `services.settings`. Dispatcher and worker gateways use their own startup settings (`apps/dispatcher/main.py:255`, `apps/dispatcher/main.py:273`, `apps/worker/main.py:119`). The save path does not propagate this configuration to execution. The actual planning mismatch is confirmed by database records; worker execution was blocked by E2E-01.

**Impact:** “Changes apply across the workspace” is misleading. Discovery works in this build; applying the selected model to planning does not.

### E2E-03 — P1: task list, graph and agent details disagree with the API

**Reproduce:** Open historical run `6acc6cff-39e5-4277-b337-71606209b1a9` → click a task in List → switch to Graph → click its research task.

List clicks do nothing. Graph shows an empty `Stage 1 0/0` and puts all six tasks in the next stage. The graph opens a drawer, but Task ID is blank, priority reads `Priority undefined`, and Agent updates displays a UUID parsing error for `task_id: "undefined"`. Run-level events also appear in task activity.

`TaskResponse` exposes `task_id`, with no `id`, `priority` or description field (`apps/api/schemas.py:108`). Rendering, graph keys, task lookup, socket/intel requests and event filtering instead use `task.id` (`apps/web/app.js:630`, `apps/web/app.js:728`, `apps/web/app.js:821`). Task activity consequently matches events whose payload lacks a task ID.

**Impact:** users cannot reliably inspect tasks or live agent output. See screenshot 05.

### E2E-04 — P1: a nonexistent repository path is silently accepted

**Reproduce:** New run → Repository folder `ui-e2e-missing-repository` → Connect repository.

The app reports a connected repository and creates starter code and a baseline commit instead of saying the folder does not exist. Connecting the actual fixture separately works.

`apps/api/routes.py:321` derives a target folder, calls `mkdir`, then initializes/scaffolds it without verifying that a typed existing repository was found. **Impact:** a typo can send work to generated starter code instead of the intended project. Repository creation should be explicit and distinct from connecting existing code.

### E2E-05 — P2: planning failures hide their actionable cause

**Reproduce:** Open the failed normal run → follow the banner's advice to inspect Activity → clear search and choose All.

Activity contains only `run.requested`; it does not show the missing-tool errors. The user is told to inspect recorded errors that are unavailable there. The errors are present in dispatcher logs and the architect stage is marked failed. **Impact:** users lack enough information to recover and may incorrectly blame connectivity or discovery.

### E2E-06 — P2: model test has a shorter timeout and a vague error

**Reproduce:** Settings with the original Nemotron model and displayed timeout 120 seconds → Test connection.

It fails after 30,020.8 ms with `FAILED` / `Error: Connection failed`. Gemma succeeds in 2,719 ms with valid JSON. Discovery lists ten models.

`/models/test` hardcodes `httpx.AsyncClient(timeout=30.0)` in `apps/api/routes.py:283`; the displayed inference timeout does not govern that test. Empty exception text becomes the generic message. **Impact:** slow local inference appears to be a connectivity failure. The timeout policy and explanation need to be explicit.

### E2E-07 — P2: invalid run lookup exposes raw validation internals

**Reproduce:** Open a run by ID → enter `not-a-real-run` → Open.

A raw UUID validation structure is displayed. Entering a valid UUID recovers and opens the run. **Impact:** API input validation works, but the UI error is confusing; validate the UUID and show an actionable message.

### Minor UI inconsistencies

- Editing a connected repository disables Start run correctly, but “Repository connected. Describe the work in step 2.” remains. Use this goal also clears the repository while retaining this success message.
- Failed and cancelled zero-task runs still show `Planning` under Task progress despite their terminal run status.
- Invalid-token submission briefly displays “Admin token saved for this session” even though loading the workspace then correctly reports token rejection.
